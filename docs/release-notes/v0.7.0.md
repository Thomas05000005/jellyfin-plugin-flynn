# Flynn v0.7.0

**Music.** The first module outside System, and the first in the area where the Jellyfin plugin
ecosystem has nothing at all — the word *ReplayGain* does not appear once across the 206
repositories in awesome-jellyfin.

It reads. It changes nothing.

## What it answers today

*How many of your tracks actually have a loudness value, and why the rest do not.*

The second half is the module. There are three ways to get that number wrong, and all three would
have produced a confident, alarming, useless card:

**The measuring is off by default.** `EnableLUFSScan` has no initialiser, and it appears in exactly
one place in the whole server besides its own declaration. A library with no measured values has
not failed at anything — that is what an untouched Jellyfin looks like. So the card says *measuring
is switched off*, which is a setting you can change in ten seconds, rather than *these tracks are
broken*, which is an accusation.

**The server reads exactly one tag.** `REPLAYGAIN_TRACK_GAIN`, one occurrence in the entire
codebase. Files carrying only an album gain, or tagged the Opus way with `R128_TRACK_GAIN`, are read
as having nothing. That is a real gap and nothing else surfaces it.

**The two values are alternatives, not a sum.** The server never measures a track whose tag it
already read, so counting both would report more covered tracks than the library holds.

## Walking 400 000 tracks without killing the server

The obvious loop — page with `StartIndex`, count, next page — is quadratic. `StartIndex` becomes a
real SQL `OFFSET`, applied *after* a `DISTINCT` over the full entity and an `ORDER BY`, so the
engine produces and throws away every row before the offset. At four hundred thousand tracks in
pages of a thousand that is tens of billions of discarded rows: a design that works on a test
library and destroys a real one.

It walks by album instead. Albums are cheap to load; their tracks come back in one query per batch
of two hundred. One linear pass.

That was the first version of this module, written and then thrown away after reading the server's
query builder.

## Also fixed: a test that was passing for the wrong reason

Two inbox tests went red on their own, a week after being written and without a line changing. They
had been comparing a snooze deadline computed from the wall clock against expiry decided by an
injected one; the dates happened to be close enough that it worked. Time passed and it stopped.

An adversarial review had flagged exactly this and it was set aside as a testability concern. It
was not — it was a test passing for a reason unrelated to what it asserted. The controller now uses
the same clock the registry does.
